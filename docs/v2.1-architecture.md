# Investment Operating System v2.1 Architecture — Personal Deployment Layer

## Status

This document is the Phase A deliverable of Issue #242 ("v2.1: Prompt-first Personal IOS
deployment kit") and stays the authoritative design/data-contract reference as later phases land —
it is not a status report, so check Issue #242 itself for exactly what's implemented as of any
given moment. As of this revision: Phase A (this document, the schema), Phase B (the GAS
Dashboard package at
[`integrations/google-apps-script/ios-dashboard/`](../integrations/google-apps-script/ios-dashboard/),
including its v1.1 visual-parity interaction/UX layer from Issue #250), Phase C (the one-prompt
installer and Daily/Weekly Task instructions under [`setup/`](../setup/)), and Phase D (user
documentation at [`docs/usage/personal-ios-dashboard.md`](usage/personal-ios-dashboard.md)) are
implemented. Phase E (the `v2.1.0` release) has been tagged and published after the real
end-to-end verification pass against a live Google Sheet + ChatGPT Scheduled Task + GAS deployment
cleared the original release gate; see
[`docs/releases/v2.1.0-verification-checklist.md`](releases/v2.1.0-verification-checklist.md) and
Issue #242.

## Why v2.1

v2.0 (`ios/`, frozen at `v2.0.0`) delivers the investment methodology, the Prompt Suite/Agent
specifications, and a deterministic, auditable research runtime. It does not provide a low-friction
way for an individual investor to *operate* IOS day to day. v2.1 closes that gap with a personal
deployment layer built entirely outside `ios/`:

```text
Google Sheets (portfolio source of truth)
        |
        v
ChatGPT Scheduled Tasks (Daily / Weekly IOS research + structured Sheet write-back)
        |
        v
Google Apps Script Web App (fixed-URL visual Dashboard: Daily / Weekly / history views)
```

- **Sheet = durable, user-controlled state.** The user's portfolio and watchlist live nowhere else;
  nothing in this layer is allowed to silently fall back to stale chat memory when the Sheet is the
  authority.
- **Scheduled Task = research + structured write.** A ChatGPT Task reads the live Sheet, runs the
  existing Daily/Weekly Prompt Suite content (`prompts/daily-investment-report.md`,
  `prompts/weekly-portfolio-report.md`), and writes its result back into the report tables defined
  below — never free-text Markdown the Dashboard would have to parse.
- **GAS Web App = presentation only.** The Dashboard reads structured Sheet rows and renders them;
  it contains no research logic and makes no investment judgments of its own.

## Product boundaries (unchanged from v2.0, restated for this layer)

v2.1 is a deployment/operating layer, not a new decision-making system. It inherits every
boundary the Book and Prompt Suite already establish, and Phase B/C implementations must not
violate any of these:

- No autonomous trading, no hidden buy/sell execution — every actual investment action remains a
  human decision.
- No fabricating a missing portfolio fact. A blank cell means unknown, not zero or "assume prior
  value."
- No silent fallback from the live Sheet to stale prompt/chat memory when the Sheet is the declared
  source of truth for that fact.
- Watchlist entries are never counted as holdings, in the schema or in any rendered view.
- Transaction history (`交易记录`) is context only — it never overrides `当前持仓`'s own state.
- The deterministic `ios/` research code gains no hidden LLM inference as a side effect of this
  work; this layer is entirely outside `ios/` and does not require the Python runtime to operate.

## Canonical Google Sheets schema

One spreadsheet, nine user-facing tabs (seven from `schema_version 1`, plus two additive
`schema_version 2` tabs — see "Account/capital facts and fund-sleeve detail (`schema_version 2`)"
below) plus one installer-owned internal tab (`_安装状态`, see "Installation-state model" below).
`schema_version 3` (Issue #267) adds no new tab -- only an additive `跟进类型` column on the
existing `报告待办` tab, see "Follow-up kind (`schema_version 3`)" below. Every tab and field name
below is authoritative for Phase B (GAS Dashboard) and Phase C (installer) — both must read/write
exactly these names, not a paraphrase. The machine-readable form is
[`setup/schema/sheet-schema.json`](../setup/schema/sheet-schema.json).

### `当前持仓` (Current Holdings)

`代码, 名称, 市场, 持有数量, 平均成本, 参考买入价/区间, 币种, 账户, 状态, 备注, 最后更新`

Only rows with `状态=持有` and `持有数量 > 0` count as current holdings. A blank `平均成本` means
unknown — never reconstructed or defaulted by any automated writer. `参考买入价/区间` is the user's
own ongoing decision anchor (e.g. "add more below 38") — distinct from `平均成本` (the actual cost
basis) and never derived from it; blank means not set, not zero.

### `交易记录` (Transactions)

`日期, 代码, 操作, 数量, 成交价格, 币种, 账户, 手续费, 备注`

History/context only. Never used to override `当前持仓`.

### `观察名单` (Watchlist)

`代码, 名称, 市场, 主题, 关注理由, 理想买入区间, 当前状态, 优先级, 最近研究日期, 备注`

Not holdings, in any view or aggregate.

## Account/capital facts and fund-sleeve detail (`schema_version 2`, Issue #259)

Two additive, **optional** tabs, introduced without touching any `schema_version 1` tab's fields,
order, or semantics — a `schema_version 1` Sheet remains fully valid and readable as-is, and
neither tab is required for the Dashboard's existing fail-closed gate (`SHEET_TABS_`/
`REQUIRED_HEADERS_` in Code.gs deliberately do not include them). They exist so the Weekly Task's
required "current cash/funding status" input (see `agents/weekly-agent.md`'s 必要输入 vs 建议输入
classification) can be sourced as a durable Sheet fact instead of the chat-only
`WEEKLY_CASH_CONTEXT_PLACEHOLDER` mechanism, and so a fund position held as a single sleeve can be
represented without fabricating per-holding cost-basis detail it doesn't have.

### `账户状态` (Account Status)

`账户, 币种, 可用现金, NISA成长投资额度剩余, NISA积立额度剩余, 本年计划追加资金, 定期定额扣款,
数据时间, 来源, 备注`

One or more rows per account/currency. `可用现金` is the only field the Weekly Task treats as
satisfying its required cash/funding input — a blank means unknown, never 0, and a tab with every
row's `可用现金` blank is treated identically to `未提供`/legacy-absent. `NISA成长投资额度剩余`/
`NISA积立额度剩余`/`本年计划追加资金`/`定期定额扣款` are 建议输入 only per
`agents/weekly-agent.md` — their absence is a noted gap, never a run-blocker. `数据时间` is
required whenever any other field on the row is populated; a stale `数据时间` is a gap note, not a
reason to discard the fact. A Sheet that has never had this tab created behaves exactly as it did
before `schema_version 2` — see "Weekly Task cash-fact source priority" below.

### `投资信托明细` (Fund Sleeve Detail)

`基金名称, 代码, 账户, 币种, NISA分类, 当前市值, 未实现盈亏, 数据时间, 备注`

One row per fund holding inside a sleeve. `当前市值` is the authoritative current value for that
fund; `未实现盈亏` is optional and never fabricated when the broker doesn't surface it. Absence of
this tab is normal — most installations will have no fund-sleeve position at all.

**FUND-SLEEVE reconciliation rule.** `当前持仓` may optionally carry one aggregate row with
`代码=FUND-SLEEVE`, representing an entire fund sleeve as a single position. That row's own
`持有数量`/`平均成本` are never used to derive the sleeve's current value or added to the sum
below — doing so would double-count the same position twice. The sleeve's true current value is
instead the sum of `投资信托明细.当前市值` across the rows matching the `FUND-SLEEVE` row's own
`账户` (or every `投资信托明细` row, if that `账户` field is blank — a whole-portfolio sleeve). A
consumer computing a portfolio total must pick exactly one of {the `FUND-SLEEVE` aggregate row, the
`投资信托明细` sum for that scope} — never both additively. The GAS Dashboard package implements
this as pure, independently tested functions (`getAccountFacts_`, `hasSuppliedCashFacts_`,
`getFundSleeveDetail_`, `reconcileFundSleeveValue_` in Code.gs) that are not yet wired into
`readAllTabs_`/`doGet` — displaying these facts in the Dashboard UI is a deliberate, documented
follow-up, not part of Issue #259.

### Weekly Task cash-fact source priority

Exactly one source is authoritative for a given Sheet, decided by the **recorded**
`_安装状态.schema_version` — never by merely whether `账户状态` happens to exist. Binding the
decision to the tab's mere presence, rather than to the recorded schema version, was tried and
rejected during Issue #259's review: a Sheet already on `schema_version 2` whose `账户状态` tab is
later deleted or renamed would then be misclassified as a pre-migration `schema_version 1` Sheet
and silently fall back to the legacy placeholder — which may hold a stale pre-migration value, or
(after the fix below) an explicit inert sentinel never meant to satisfy the input. Either way that
recreates the hidden, unintended fallback #259 exists to forbid; a missing/unreadable `账户状态`
tab under a recorded `schema_version >= 2` is a **schema-incompatible state and must be `Blocked`**,
not reinterpreted as an older Sheet.

0. **Read `_安装状态.schema_version`.** A read failure on `_安装状态` itself is `Blocked`. A
   confirmed-absent `_安装状态` tab (a Sheet older than the installation-state mechanism itself) is
   treated as `schema_version 1`.
1. **`schema_version >= 2`: `账户状态` is the sole source, full stop.** A read failure on the tab is
   `Blocked`. A confirmed-absent tab is *also* `Blocked` (schema-incompatible — the recorded version
   says the tab should exist) — never falls through to step 2. A tab present with at least one row
   whose `可用现金` is non-blank satisfies the required input. A tab present but with every row's
   `可用现金` blank (or zero rows) means the required input is missing — this does **not** fall
   through to the legacy placeholder; the gap note directs the user to add a real row to
   `账户状态`, not to edit an inert legacy field.
2. **`schema_version == 1`** (or `_安装状态` confirmed absent): **Legacy
   `WEEKLY_CASH_CONTEXT_PLACEHOLDER`** — the original mechanism, byte-for-byte unchanged: an
   installer-time chat answer embedded directly into the Weekly Task's own instructions.

Either way, a missing required input blocks the **entire** Weekly run (not just the
capital-allocation section) per `agents/weekly-agent.md`. The installer reflects this same
single-source model on the write side (see `setup/chatgpt-install-prompt.md` Step 4): once a Sheet
is on `schema_version 2`, the installer collects real `账户状态` rows (or leaves the tab empty if
the user declines) and no longer asks the legacy chat question at all. It also **retires**
`weekly_cash_context`: both the Task template's line and `_安装状态.weekly_cash_context` are
overwritten with a fixed, explicit inert sentinel (never left as the raw unsubstituted placeholder
marker, and never left holding a stale pre-migration description) — a residual placeholder marker
would otherwise contradict the installer's own "no residual placeholders" completion rule. The
legacy question-and-answer flow is used only for installs that stay genuinely on
`schema_version 1` after the run.

### `报告摘要` (Report Summary)

`报告ID, 生成ID, 报告类型, 报告日期, 周期开始, 周期结束, 一句话结论, 核心状态, Review状态, 当前持仓数, 高优先级观察数, 生成时间, 备注`

### `报告持仓` (Report Assets)

`报告ID, 生成ID, 报告类型, 报告日期, 资产类型, 代码, 名称, 数量, Thesis状态, IOS状态, 关键变化, 长期逻辑或估值, 下一验证点, 参考买入价/区间, 当前价格, 价格位置, 优先级, 排序`

`参考买入价/区间`/`当前价格`/`价格位置` are a report-time *snapshot* (for `资产类型=holding`, copied
from `当前持仓`; for `资产类型=watchlist`, derived from `观察名单.理想买入区间`) — a historical report
row must stand on its own rather than depend on a live value that may have since changed (see
"Schema migration policy" below on why report rows aren't disposable). `价格位置` is the writer's
qualitative placement of price relative to the reference (e.g. "低于区间") — descriptive only, never
a computed buy/sell signal, and the Dashboard renders it verbatim rather than deriving it.

### `报告风险` (Report Risks)

`报告ID, 生成ID, 报告类型, 报告日期, 风险类型, 风险, 影响资产, 影响, 本期动作, 严重度, 排序`

### `报告待办` (Report Todos)

`报告ID, 生成ID, 报告类型, 报告日期, 排序, 分类, 待办, 状态, 备注, 跟进类型`

`生成ID` is new as of this revision (Phase A review round 1) — see "Report write protocol" below
for why a second identifier is required alongside `报告ID`. `跟进类型` is new as of `schema_version
3` (Issue #267) — see "Follow-up kind (`schema_version 3`)" below.

## Follow-up kind (`schema_version 3`, Issue #267)

`报告待办`'s existing `状态` field is a completion state (`待处理`/`已完成`) — it says nothing about
*why* an item is unresolved. In real operation, several generated follow-ups are not one-time
actionable work: an ongoing condition worth tracking across future reports (e.g. "continue
monitoring a chip product's capacity ramp/margins/inventory"), or an item genuinely blocked on a
future external event (a board decision, a filing, a regulatory approval) with no available next
step until then. Representing either as an ordinary unresolved `待处理` row makes the Dashboard's
todo/backlog view look like work is accumulating or something has been left unfinished, when
nothing has actually been missed.

`跟进类型` is an additive, optional enum on `报告待办` distinguishing exactly this:

- `可执行` — actionable work the user/Agent can advance now.
- `持续观察` — an ongoing condition or metric to keep tracking across future reports; not a
  one-time task, and its recurrence in report after report is expected, not a sign of neglect.
- `等待证据` — blocked on a specific future external event; no useful action exists until then.

Rules:

- `跟进类型` is orthogonal to `状态`. A `持续观察`/`等待证据` row normally stays `待处理` for as long
  as the condition it describes remains active; it moves to `已完成` only once that follow-up item
  itself is genuinely concluded (the condition stopped mattering, or the awaited event happened) —
  never simply to make the Dashboard's backlog count look smaller.
- Blank or any value outside the three-value enum is treated as `可执行` by every reader (the GAS
  Dashboard, and any future consumer) — the same safe, conservative default `状态`'s own classifier
  already uses for an unrecognized value (see "Todo status classifier" precedent, Issue #260).
  Every `报告待办` row written before this schema version has no `跟进类型` column at all, and reads
  identically to a row whose `跟进类型` is `可执行` — no historical row needs rewriting.
- `跟进类型` only classifies presentation grouping. It must never be used to infer or imply
  investment meaning (a buy/sell signal, an urgency score, a thesis judgment) — that stays outside
  this field's job per the Book/Prompt Suite's existing boundaries, same as `价格位置`'s own
  "descriptive positioning only" rule above.
- The GAS Dashboard groups a report's open todos as actionable-first, then ongoing-monitoring, then
  waiting-for-evidence, then completed last — so genuinely actionable work is never buried behind
  non-backlog groups, and the `待处理` count in the Dashboard's summary badge reflects only the
  actionable-and-unresolved group. The `持续观察`/`等待证据` summary badges render only when that
  group is non-empty, so a Sheet that has never used `跟进类型` (every row classifies as
  `可执行`) renders identically to the pre-Issue #267 Dashboard.
- The Daily/Weekly Scheduled Task instructions (`setup/daily-task-prompt.md`,
  `setup/weekly-task-prompt.md`) are responsible for populating `跟进类型` when writing new
  `报告待办` rows — this is a structured-output/schema-classification requirement layered at the
  Task-instruction level, the same way `分类`/`排序` are already populated without those Task
  instruction files redefining any investment judgment the frozen Prompt Suite already owns.

## Daily/Weekly structured report contract

The four `报告*` tabs above are the entire contract between a Scheduled Task (writer) and the
Dashboard (reader) — the Dashboard never parses Markdown.

- **Report id.** `daily-YYYY-MM-DD` / `weekly-YYYY-MM-DD` (the Monday-anchored ISO date of the
  report's own `报告日期`, not the run timestamp). This is the stable business key a user or the
  Dashboard's history selector refers to a report by.
- **Content authority.** Daily reports are produced against the current `agents/daily-agent.md` +
  `prompts/daily-investment-report.md`; Weekly reports against
  `prompts/weekly-portfolio-report.md`. The report contract only constrains *where the output
  lands*, never what judgment the Prompt Suite is allowed to reach — Prompt Suite behavior is
  frozen at `prompts-v1.0.0` and this layer does not get to reinterpret it.
- **Blocked vs. a valid empty result.** These are not the same thing, and Task logic must not
  conflate them:
  - **Blocked** — the Task could not obtain a required input at all: a tab is unreadable, a
    required column is missing, or the Sheet's `schema_version` is one the Task doesn't know how
    to handle. The Task writes `核心状态`/`Review状态` stating this explicitly — the equivalent of
    `ios/workflows`' `insufficient_evidence`, expressed in this schema's own vocabulary — rather
    than silently producing a thinner report.
  - **Valid empty result** — a tab was read successfully and simply has zero matching rows (an
    empty `观察名单`, or a user genuinely holding no positions in `当前持仓`). This is legitimate
    portfolio state, not a failure, and must never trigger `Blocked` or any equivalent degraded
    status. A report about an empty watchlist is still a complete, valid report.

## Report write protocol (atomic commit across four tabs)

A single `报告ID` is realized as one row in `报告摘要` plus a variable number of rows spread across
`报告持仓`/`报告风险`/`报告待办` — four separate writes the Sheets API has no native way to commit
as a single transaction. A Task that fails partway through a naive "delete old rows, write new
rows across four tabs" sequence can leave `报告ID` pointing at a mix of old and new data, or at no
data at all. The protocol below makes each report id's *published* state atomic despite that,
using only an ordinary spreadsheet's own guarantees (a single row write to a single tab is atomic;
nothing broader is assumed):

1. **Generate.** Every write attempt for a given `报告ID` — first attempt or retry — mints a fresh
   `生成ID` (e.g. a UUID). A `生成ID` is never reused across attempts, including retries of a
   previously failed attempt.
2. **Stage.** Write every `报告持仓`/`报告风险`/`报告待办` row for this run, tagged with
   `(报告ID, 生成ID)`. The existing `报告摘要` row for this `报告ID` (if any) is *not* touched yet —
   readers still see the last known-good generation throughout this step.
3. **Verify.** Read back the rows just written for `(报告ID, 生成ID)` and confirm they match what
   was intended (count and content). If verification fails, the run stops here: the new rows are
   orphaned (see step 6) and `报告摘要` is left completely untouched.
4. **Switch.** Only after verification succeeds, write (create or update) the single `报告摘要` row
   for `报告ID`, setting its `生成ID` field to the new value. A single row write is the one
   operation this protocol treats as atomic — it either lands or it doesn't, so this is the actual
   commit point. Before this step, nothing published has changed; after it, the new generation is
   the published one.
5. **Read contract.** A reader (Dashboard or Task) treats a `报告持仓`/`报告风险`/`报告待办` row as
   live *only* if its `生成ID` matches the `生成ID` currently found in that `报告ID`'s `报告摘要`
   row. Rows tagged with any other `生成ID` are stale/orphaned and are never rendered or aggregated.
6. **Cleanup (best-effort, not required for correctness).** After a successful switch, detail rows
   from the previous generation (and, if step 3 failed, the never-published generation from this
   attempt) are safe to delete — the read contract in step 5 already makes them inert. Cleanup may
   happen on the next successful run for the same `报告ID`, or on a periodic sweep; it is never a
   precondition for the report being correct or usable.
7. **Failure and retry.** If the Task's own run fails at any point before step 4 completes,
   `报告摘要` still points at the last known-good `生成ID` (or doesn't exist yet, for a first
   attempt) — the report a user sees is never partial. The failed run is reported through the
   Task's own run status/notification (not by writing anything into `报告摘要`). Retrying simply
   repeats this protocol from step 1 with a new `生成ID`; because step 5's read contract only ever
   trusts the `生成ID` `报告摘要` currently references, a half-written retry can never be confused
   with a complete one, no matter how many failed attempts preceded it.

## Schema migration policy

`setup/schema/sheet-schema.json`'s `schema_version` may need to advance as this deployment layer
evolves. The default for **every** tab, including the four `报告*` tabs, is additive-preferred and
history-preserving:

- A schema migration must not delete or rewrite existing rows in any tab by default — a historical
  report row is not necessarily reproducible by re-running the Task that produced it (the market
  data, filings, or prices behind it may no longer be obtainable the same way later), so it cannot
  be treated as disposable just because it is "system-generated."
- The atomic replace protocol above is a normal *write-time* operation scoped to one `报告ID`'s own
  re-run (a new `生成ID` for that same id) — it is not a schema migration, and schema migration
  logic must not reuse it as a general-purpose "safe to rewrite" excuse.
- Any migration step that is genuinely destructive (renaming/removing a field in a way existing
  rows can't be read against, or otherwise not expressible additively) must be its own explicit,
  versioned step with a backup taken first, a documented rollback, and explicit user approval
  before it runs against a real installation — never silently bundled into an ordinary installer
  upgrade.
- Each schema version bump is recorded in `sheet-schema.json`'s own top-level `schema_changelog`
  array (version, originating issue, `additive`/`destructive` kind, a summary, and the migration
  an installer performs) — the schema file documents its own history rather than relying on prose
  elsewhere staying in sync. `schema_version 2` (Issue #259, adding `账户状态`/`投资信托明细`) is
  the first entry and is purely additive: an installer upgrading a `schema_version 1` Sheet adds
  the two new tabs (header-only, no example data) and bumps `_安装状态.schema_version` to `2`; a
  Sheet that is never upgraded keeps working exactly as it did under `schema_version 1`.
  `schema_version 3` (Issue #267, adding `报告待办.跟进类型`) is the second entry, also purely
  additive: an installer upgrading a `schema_version 1` or `2` Sheet adds the `跟进类型` column
  header to the existing `报告待办` tab (no backfill of historical rows' cells) and bumps
  `_安装状态.schema_version` to `3`; every reader treats a `报告待办` row without this column
  identically to one whose `跟进类型` is `可执行` (the safe default), so nothing about a
  not-yet-upgraded Sheet's existing behavior changes.

## Installation-state model

Tracked so an installer run (Phase C) can detect an existing installation and upgrade rather than
duplicate. Machine-readable form:
[`setup/schema/installation-state.json`](../setup/schema/installation-state.json).

| Field | Purpose |
| --- | --- |
| `schema_version` | Version of the Sheet schema this installation was created/upgraded against. |
| `spreadsheet_id` / `spreadsheet_url` | The user's own Sheet — never committed to this repository. |
| `dashboard_url` | The GAS Web App `/exec` URL, once the user completes the manual deploy step. |
| `daily_task` / `weekly_task` | Identity/schedule of the two Scheduled Tasks (timezone-qualified). |
| `timezone` | User's local timezone, used for both schedules and `最后更新`/`生成时间` stamps. |
| `report_table_names` | The four report tab names, in case a future version renames them. |
| `locale` | Optional; drives which language the Dashboard/Task-facing copy renders in. |

No credentials or secrets belong in this state — it identifies *where* the user's own resources
are, never how to authenticate to them. Phase C persists this model concretely as the single data
row of the `_安装状态` tab (part of `sheet-schema.json`, not a separate file) — an installer-owned,
non-user-facing tab the installer creates once and re-reads/updates on every subsequent run.
Upgrade detection matches the Daily/Weekly Tasks by the exact `daily_task_name`/`weekly_task_name`
recorded there, never by fuzzy/substring matching over the Task platform's own list — a review
finding on the first Phase C installer draft, which used name-similarity matching that could bind
to the wrong Task or create duplicates.

A read failure must never be treated the same as a confirmed-absent tab. Only a rerun that
**successfully reads the Sheet and conclusively confirms `_安装状态` is not present** may treat the
installation as a pre-`_安装状态` legacy install and enter the additive bootstrap path (a second
review finding, on the first draft's fail-open handling — that draft treated *any* failure to read
`_安装状态`, including a permission/API error or timeout, as "must be a new install," which risks
duplicate Tasks or unintended mutation against a Sheet the installer never actually confirmed the
state of). A rerun where the Sheet or the tab itself could not be read at all is **Blocked**: no
Sheet structure change, no Scheduled Task creation or update, until the user resolves access or the
transient failure clears.

## Post-install onboarding (Issue #273)

A fresh installation's `当前持仓`/`观察名单` are empty by design — the installer never invents a
holding. That left a gap between "installation complete" and "IOS can produce a useful first
report": no guided path existed to either record an existing portfolio or start from zero.
[`setup/onboarding-prompt.md`](../setup/onboarding-prompt.md) closes it as a conversational,
optional, deferrable step the installer hands off to once its own verification checklist
completes (`chatgpt-install-prompt.md`'s own "第 8 步").

It introduces no new Sheet tab or field — it only writes against the existing `当前持仓`/`观察
名单`/`账户状态` schema, through the same confirm-before-write, blank-preservation, and
no-autonomous-trade boundaries the rest of this layer already enforces:

- **已有持仓 (existing portfolio)**: accepts natural-language description, and — where the ChatGPT
  session supports it — a screenshot or CSV/Excel upload. Every extraction is provisional: it goes
  through a confirmation preview naming which fields were determined and which are still blank
  before anything is written to `当前持仓`, and a candidate that matches an existing row by
  `代码`(+`账户`) is never silently overwritten — the user is asked how to reconcile it. An optional
  follow-up offers to record `账户状态` facts, reusing the installer's own ask/decline pattern (never
  asked twice if the installer already covered it).
- **从零开始 (zero-holdings start)**: a short, progressive interview (horizon, capital, liquidity,
  risk tolerance, markets/exclusions, and non-Sheet exposures used only as background, never
  written anywhere) produces a user-confirmed "investment starting profile," then a small,
  explainable research candidate pool — each candidate states why it's relevant, its key risks,
  what to verify next, and whether it's watchlist-suitable. The pool is a research prompt, never an
  auto-generated buy list; a candidate only reaches `观察名单` after the user selects it for further
  research and explicitly confirms.

Both routes hand control back to normal usage the same way: the Sheet is the sole authoritative
input for Daily/Weekly Tasks from that point on, and the onboarding conversation itself is never
treated as a stale substitute once it ends. The GAS Dashboard's own empty-state card (shown before
any report exists) points to this flow as a next step, but the Dashboard itself runs no profile
analysis or candidate generation — that judgment stays in the conversational/research layer, per
this layer's existing "GAS Web App = presentation only" boundary above.
