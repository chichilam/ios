# Investment Operating System v2.0 Architecture Overview

本文是 [v2.0 Roadmap](v2.0-roadmap.md) 的架构落地文档。

它把 Roadmap 中的愿景、Epic 划分和依赖模型，转化为一份具体的架构蓝图，供后续 Epic Issue 引用。

本文不实现任何代码。它只定义系统边界、接口、依赖关系和数据流。

---

## 1. 架构原则

v2.0 架构建立在以下原则之上：

- **Book 保持投资哲学的唯一来源**。Book 已在 `book-v1.0.0` 冻结，v2.0 不改写投资哲学、不新增投资框架。
- **Prompt Suite 保持工作流规范层**。Prompt Suite 已在 `prompts-v1.0.0` 冻结，v2.0 按需扩展 prompt，不改变已冻结的执行边界。
- **Agent Runtime 执行工作流，但不做自主投资决策**。Agent Runtime 调度 Prompt Suite 定义的工作流，产出研究结论和决策建议，但不代替人执行任何投资行动。
- **所有投资行动都需要 Human Review**。买入、卖出、调仓等任何实际执行动作，必须经过人工确认，Agent Runtime 不具备自动交易能力。
- **接口应保持模型中立和工具中立**。任何对外接口（Tool / Data Provider Interface、Research Store Interface、Knowledge Query Interface 等）不得绑定特定模型供应商或特定工具实现，以保证底层实现可替换。

---

## 2. 系统分层

v2.0 由以下层级组成，每层职责单一：

| 层级 | 职责 | 状态 |
| --- | --- | --- |
| Book | 定义投资哲学、原则和决策标准 | 已冻结（`book-v1.0.0`） |
| Prompt Suite | 把投资原则转化为可执行 AI 工作流 | 已冻结（`prompts-v1.0.0`），按需扩展 |
| Agent Runtime | 调度和执行 Prompt Suite 定义的工作流；管理 Planner、Research Agent、Portfolio Agent、Reviewer、Critic、Memory | v2.0 新增 |
| Tool / Data Provider Interface | Agent Runtime 调用外部数据和工具的抽象接口 | v2.0 新增 |
| MCP Integration Adapters | 实现 Tool / Data Provider Interface，连接 GitHub、Notion、Gmail、Calendar、市场数据、模型供应商 | v2.0 新增 |
| Research Engine | 执行个股、行业、宏观、IPO 研究工作流 | v2.0 新增 |
| Research Store Interface | 研究输出的最小读写接口 | v2.0 新增 |
| Knowledge Query Interface | 检索、历史论点查询、知识图谱读取接口 | v2.0 新增（Milestone 3） |
| Knowledge Base | 完整知识存储：公司数据库、投资论点库、决策历史、知识图谱；同时实现 Research Store Interface 和 Knowledge Query Interface | v2.0 新增 |
| Portfolio Operating System | 仓位追踪、配置引擎、买卖决策支持、风险监控 | v2.0 新增 |
| Evaluation Framework | 评估 Prompt 质量、Agent 输出质量、研究结论准确性；贯穿所有层 | v2.0 新增（最小子集起步） |
| Human Review Layer | 对所有投资行动的最终人工确认边界 | v2.0 新增，贯穿全流程 |

## 3. 依赖模型

延续 [v2.0 Roadmap](v2.0-roadmap.md) 中确立的非循环依赖设计：

- **Agent Runtime 定义 Tool / Data Provider Interface**。这是一个抽象接口，Agent Runtime 核心框架只依赖这个接口本身，不依赖任何具体数据源的实现。
- **MCP Integration 实现该接口的适配器**。GitHub、Notion、Gmail、市场数据等连接器都是 Tool / Data Provider Interface 的具体实现（Adapter），与 Agent Runtime 核心框架并行开发。
- **Research Engine 依赖 Research Store Interface，而非完整 Knowledge Base**。这是一个最小读写接口，Research Engine 只需要能记录和读取研究输出，不需要检索、知识图谱等能力。
- **Knowledge Base 后续替换最小 research store 的实现**。Research Store Interface 本身保持不变，Knowledge Base 在底层提供完整的数据模型和知识老化策略。
- **检索能力通过独立的 Knowledge Query Interface 提供，而非扩大 Research Store Interface**。Knowledge Base 同时实现两个接口：Research Store Interface（兼容既有写入路径）和 Knowledge Query Interface（Milestone 3 新增，提供条件检索、历史论点查询、知识图谱读取）。这样接口边界清晰，也不需要为了暴露高级能力而破坏原有接口的最小契约。
- **Evaluation Framework 从最小子集起步，逐步扩展**。不是等所有 Epic 完成后才开始评估；输出结构校验和任务完成率追踪从 Agent Runtime 可执行的第一天就同步交付，完整指标体系随各层成熟逐步补齐。

这个依赖模型的核心目的：**任何两个 Epic 之间都不互相依赖对方的完整实现**，只依赖一个稳定的接口。这样各 Epic 可以并行拆分为独立 Issue，不会因为等待另一个 Epic 完工而阻塞。

## 4. 数据流

数据流分为两条线：**控制流**（谁调度谁）和**数据返回流**（数据实际如何流回调用方）。把 MCP Adapter 画成业务顺序中的一层容易让人误以为它会把控制权交给下一层——实际上 Adapter 只是接口的具体实现，负责返回标准化数据，不参与业务编排。

```text
User / Schedule / Event
        ↓ 触发
Agent Runtime
        ↓ 调度
Research Engine
        ↓ 请求数据 / 工具               ↑ 返回标准化结果
Tool / Data Provider Interface ──────── MCP Adapters / Data Sources
        ↓
Research Engine（消费数据，执行研究工作流）
        ↓ 写入
Research Store Interface
        ↓
Knowledge Base
        ↓
Portfolio Operating System
        ↓
Human Review
```

说明：

- 触发源可以是用户请求、定时调度或外部事件（例如财报发布、IPO 申报）。
- Agent Runtime 接到触发后，调度 Research Engine 执行具体研究任务；Agent Runtime 掌握业务编排的控制权。
- Research Engine 通过 Tool / Data Provider Interface 请求所需数据和工具能力，不关心背后是哪个具体数据源。
- MCP Adapters 只是该接口的实现：接到请求后连接外部系统，把原始数据转换为标准格式，**返回**给 Research Engine——Adapter 不发起业务流程，也不决定下一步做什么。
- Research Engine 消费返回的数据，执行 Prompt Suite 定义的研究工作流，产出结构化研究结论。
- 研究结论通过 Research Store Interface 写入，短期内由最小存储实现，长期由 Knowledge Base 承接。
- Knowledge Base 中积累的知识通过 Knowledge Query Interface 被检索，为 Portfolio Operating System 的配置和决策支持提供依据。
- 任何从研究结论到实际投资行动的转化，都必须先经过 Human Review，Agent Runtime 不能跳过这一步直接执行。

Evaluation Framework 不在这条主流程之内，而是贯穿每一层，持续评估每一层输出的质量。

## 5. 接口边界

### Tool / Data Provider Interface

**负责**：
- 定义 Agent Runtime 请求外部数据或调用外部工具的统一契约（输入格式、输出格式、错误处理约定）。
- 保持模型中立和数据源中立，使 Agent Runtime 核心逻辑不因更换数据源或模型供应商而改变。

**不得**：
- 绑定具体 MCP 服务商或具体 API 的实现细节。
- 包含任何投资判断逻辑——这属于 Prompt Suite 和 Research Engine 的职责。

### Research Store Interface

**负责**：
- 定义研究输出的最小读写契约：写入一条研究记录、按标识读取一条或多条研究记录。
- 为 Research Engine 提供与存储实现无关的持久化能力。

**不得**：
- 提供检索、排序、知识图谱等高级能力——这些能力由 Knowledge Query Interface 提供（见下），不通过扩大本接口来实现。
- 对研究内容做投资判断或质量评分——这属于 Evaluation Framework 的职责。

### Knowledge Query Interface

Milestone 3 新增，与 Research Store Interface 是两个独立接口，而非同一接口的扩展版本。Knowledge Base 同时实现 Research Store Interface（兼容 Research Engine 的既有写入路径）和 Knowledge Query Interface（提供新增查询能力），两者互不影响。

**负责**：
- 定义条件检索、历史论点查询、决策历史查询的契约。
- 定义知识图谱的读取契约：查询公司、行业、宏观因素之间的关联关系。
- 为 Agent Runtime / Research Engine 提供跨记录的查询能力，而不仅是按标识读写单条记录。

**不得**：
- 承担写入职责——写入路径始终经过 Research Store Interface，Knowledge Query Interface 只读。
- 对查询结果做投资判断——检索到的历史论点和知识图谱关系仅作为参考信息，是否采纳仍由 Research Engine 的工作流和 Human Review 决定。

### Human Review 边界

**负责**：
- 拦截所有从研究结论/决策建议到实际投资行动之间的转化路径。
- 提供明确、可审计的人工确认记录。

**不得**：
- 被 Agent Runtime 自动绕过，无论触发源是用户请求还是定时调度。
- 与研究质量评估（Evaluation Framework）混淆——Human Review 针对的是"是否执行"，Evaluation Framework 针对的是"输出质量如何"。

Human Review 的核心边界是实际投资行动必须人工确认，这一点不因工具调用方式而改变。除此之外，任何可能触发外部写操作、通知或其他高影响动作的工具调用（例如写入 Notion、发送邮件），也应在 Tool / Data Provider Interface 层预留 policy gate 钩子，具体策略由后续 Epic Issue 定义。

### Evaluation 边界

**负责**：
- 评估 Prompt 输出结构一致性、Agent 任务完成率、研究结论质量。
- 提供回归基准，防止后续变更引入质量退化。

**不得**：
- 替代 Human Review 做出是否执行投资行动的判断。
- 直接修改 Prompt Suite 或 Agent Runtime 的行为——评估只产出信号，改进决策仍需通过正常的 Issue → PR → Review 流程。

## 6. 非目标

本文档不包括、也不在本 Issue 范围内实现：

- Agent Runtime 的实际运行时代码
- MCP 连接器的具体实现
- 市场数据接入的具体实现
- Portfolio 数据库的具体实现
- 自动化交易执行
- 新的投资哲学或投资框架

这些属于后续各 Epic Issue 的实现范围，本文档只提供它们共同引用的架构基线。
