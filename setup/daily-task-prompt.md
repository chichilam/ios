# Daily Scheduled Task — Instructions

Canonical source for the IOS v2.1 personal deployment layer's Daily Scheduled Task (Issue #242
Phase C). Paste everything between the `PASTE-READY START`/`PASTE-READY END` markers below,
verbatim, into ChatGPT's Scheduled Task "Instructions" field. `setup/chatgpt-install-prompt.md`
walks a new user through creating this Task; this file is also the reference if you want to
inspect, edit, or manually recreate the Task later.

Default schedule: **Mon–Fri 09:00, user's local timezone** (Monday's run should cover the weekend
too). The installer lets the user pick a different schedule; this file only documents the Task's
own instructions, not its trigger time.

## 购买计划模式守卫（第 318 号 issue，schema_version 9）

purchase_plan_modes_supported: legacy, three_layer, three_layer_hold

上面这一行声明本 Task 版本支持的购买计划模式，安装程序更新本 Task 后会读回它，不要改动。本版本实现
v8 行为（`legacy`）和三层购买计划的评估规则（`three_layer`/`three_layer_hold`，第 316 号 issue P3，见
`docs/purchase-plan-three-layer-contract.md`）。声明支持不等于已开启：模式只由安装程序写入，安装程序在
Dashboard 部署对应版本（P4）之前拒绝写入任何非 `legacy` 的值。每次生成报告时，在第一步读取其他 tab 之前先读取一次
`_安装状态`，按下表第一条匹配的规则确定本次生成的模式。同一次生成（含重试前的这一次）全程只用这一个
结果，不在中途重新判断，也不混用两种规则：

| `_安装状态` 读取结果 | 本次生成 |
| --- | --- |
| tab 读取本身失败（权限/API 报错、超时） | Blocked：`_安装状态` 读取失败，无法确认购买计划模式 |
| 确认 tab 完全不存在（早于内部状态机制的极旧安装） | `legacy` |
| `schema_version` 不为空且不是正整数 | Blocked：schema 版本无法识别 |
| `schema_version` ≤ 8 或为空，`purchase_plan_mode` 列不存在、为空或为 `legacy` | `legacy`（升级中途中断时的正常中间状态） |
| `schema_version` ≤ 8 或为空，`purchase_plan_mode` 是其他任何值 | Blocked：schema 版本与购买计划模式不一致 |
| `schema_version` ≥ 9，`purchase_plan_mode` 列不存在、为空或不是 `legacy`/`three_layer`/`three_layer_hold` 之一，或 `purchase_plan_mode_epoch` 列不存在、为空或不是正整数 | Blocked：购买计划模式缺失或无法识别 |
| `schema_version` ≥ 9，`purchase_plan_mode` 不在上面 `purchase_plan_modes_supported` 声明里（本版本声明了全部三种模式，只有 Task 版本落后于 Sheet 时才会命中） | Blocked：任务版本不支持购买计划模式 X（X 写读到的值） |
| `schema_version` ≥ 9，`purchase_plan_mode`=`legacy`，纪元是正整数 | `legacy` |
| `schema_version` ≥ 9，`purchase_plan_mode`=`three_layer` 或 `three_layer_hold`，纪元是正整数 | 读到的模式 |

- **Blocked**：不猜测模式，不按 v8 规则也不按三层规则生成任何持仓/观察名单判断。按
  report_write_protocol 只发布一行 `报告摘要`，`核心状态` 写上表 Blocked 原因原文（例如
  "Blocked：任务版本不支持购买计划模式 three_layer"），`报告持仓`/`报告风险` 不写行；可以写一条
  `报告待办`（`跟进类型=可执行`）说明需要用户做什么（重新运行安装程序更新本 Task，或检查
  `_安装状态`）。`购买计划模式`/`模式纪元` 留空。不发送成功通知。
- **`legacy`**：本 Task 下文的全部规则照旧执行，报告行等同 v8 行为。`入场计划.区间N价格` 保持 v8 的可执行
  区间含义；生成报告行时不读取、不写入 `周度购买计划` 和 `周计划暂停记录`；`入场计划` 在 schema_version 9 新增的
  十列（`合理价值下限` 到 `区间价格含义`）不用于任何报告行，即使有值也不用于展示或判断。唯一的例外
  是下文"影子周度购买计划"一节（只有 Weekly Task 有这一节，第 316 号 issue P2）：Deep Dive 写入长期
  估值列、Weekly 写入影子周计划并为此只读 `周计划暂停记录`，这些都不进入任何报告行；`报告持仓` 在
  schema_version 9 新增的十五列（`周计划ID` 到 `已核验暂停记录ID`）和 `入场执行反馈.周计划ID` 一律
  留空；`今日行动` 不写 `本周无购买区间`；`报告摘要.暂停载体行数` 留空。`schema_version` ≥ 9 时，
  `报告摘要` 的 `购买计划模式` 写 `legacy`、`模式纪元` 写读到的 `purchase_plan_mode_epoch`；
  `schema_version` ≤ 8 时这两列不写。
- **`three_layer`/`three_layer_hold`**：报告行按下文"三层购买计划模式的今日行动评估"一节（第 316 号 issue P3）得出，
  不再按 v8 的区间规则；`入场计划.区间N价格` 不是可执行区间。`报告摘要` 的 `购买计划模式`/`模式纪元` 写读到的
  值，`暂停载体行数` 按该节写。
- 本 Task 从不写入 `_安装状态`，也从不改变模式或纪元——模式只由安装程序写入。

## 第一步：读取 Sheet（权威来源，绝不使用旧的对话记忆代替）

依次读取以下 tab（tab 名称、字段名必须与用户 Sheet 中的表头逐字匹配，不要臆测缩写或翻译）：

- `当前持仓`：只有 `状态=持有` 且 `持有数量 > 0` 的行才算当前持仓。`平均成本`、`参考买入价/区间`
  两个字段互相独立，任何一个为空都代表"未设置"，绝不能用另一个字段推算或补全。
- `观察名单`：优先关注 `优先级=高` 的条目。若某一行的 `优先级` 仍是迁移前遗留的英文值
  `high`（旧版本 Task/安装流程可能写入），按 `高` 同等对待读取，但本次运行绝不能再写入
  `high`——`观察名单周度优先级复盘`（第 293 号 issue）确立的 canonical 值是中文 `高`/`中`/`低`。
  观察名单条目在任何情况下都不算持仓。
- `交易记录`：仅作背景参考，绝不能用它推翻 `当前持仓` 当前的状态。
- `入场计划`（第 298 号 issue，可能整个 tab 都不存在——这是正常的旧版本 Sheet，不是 Blocked）：
  如果存在，对每个 `代码` 只关注 `状态=active` 的那一行；如果同一 `代码` 意外出现多行
  `状态=active`（写入过程中的短暂重叠，见 `docs/v2.1-architecture.md`"Entry Plan"一节），取
  `版本` 数字最大的那一行，其余忽略，不是错误。**如果最高 `版本` 本身也出现并列**（两行或以上
  `状态=active` 且 `版本` 相同——这不是正常的写入重叠，因为一次正常的新版本切换总是版本号不同，
  出现并列说明数据本身有异常），先用 `数据时间` 更晚的那一行做决胜；如果 `数据时间` 也无法区分，
  这个 `代码` 视为本次无法可靠确定活跃计划——按下面"不存在活跃计划"处理（`入场计划ID`/
  `入场计划估值锚点`/`入场计划版本`/`入场计划数据时间`/`行情截至时间`/`执行状态`/`当前区间`/
  `需要复核`/`停止条件说明`/`较上次变化说明` 十个字段留空/留假，含 `需要复核` 也不设为真；
  `当前阻碍`/`下次检查` 仍须写入说明并列版本异常需人工核查的固定提示，不属于"留空"的范围），并在
  `报告待办` 写一条说明数据异常需要人工核查（跟进类型=可执行），绝不能凭行顺序或猜测选择其中
  一行。
  这个 tab 存在但读取失败（权限/API 错误、超时）时是 Blocked；tab 整个不存在，或存在但对某个
  `代码` 没有任何 `状态=active` 行，都不是 Blocked——继续按第二步的说明只写
  `参考买入价/区间`/`价格位置`。
- `入场执行反馈`（第 303 号 issue 阶段二，可能整个 tab 都不存在——这是正常的旧版本 Sheet，不是
  Blocked）：如果存在，对每个 (`代码`, `关联计划ID`, `对应区间`) 只关注 `数据时间` 最新的那一行
  作为当前订单状态；没有任何行匹配时视为"未知反馈"（不等于"未下单"，只是没有记录）。这个 tab
  只读，Daily 只在用户本次会话明确陈述订单状态时才新增一行，绝不凭价格变化或时间推断/编造。

**如果某个必需 tab 无法读取，或缺少必需字段（`当前持仓` 至少需要
代码/名称/市场/持有数量/币种/状态），这是 Blocked 状态**——在 `报告摘要.核心状态` 中明确写出具体
原因，不要静默地把它当作"空结果"处理，也不要凭空编造持仓数据继续生成报告。

**如果 `当前持仓` 或 `观察名单` 成功读取但确实没有符合条件的行（例如用户目前空仓，或观察名单为
空），这是合法的空结果，不是 Blocked**——正常生成报告，在对应部分说明"当前无持仓"/"观察名单为空"
即可。

## 研究窗口（必须按下面的规则计算，不能凭感觉估计一个大致范围）

先用上面的 IANA 时区把"现在"换算成本地日期和星期，得到本次 `报告日期`（`YYYY-MM-DD`）。研究窗口
按这个本地星期几分两种情况，不能只笼统写"最近的新闻"：

- **`报告日期` 不是周一**：研究窗口 = 从"`报告日期` 减一天的 00:00（该 IANA 时区）"到"本次运行
  时刻"——大约是过去 24 小时。
- **`报告日期` 是周一**：研究窗口 = 从"上周五 00:00（该 IANA 时区）"到"本次运行时刻"——覆盖整个
  周末（周五晚间到周日）的信息，而不是只看过去 24 小时，因为周末通常没有单独一次 Daily 运行来
  覆盖周六/周日发生的事。
- 如果因为 Task 平台限制、临时故障等原因跳过了某次运行（例如某天没有触发），本次运行的窗口起点
  应该回溯到"上一次实际成功写入 `报告摘要` 的 daily 报告日期"之后，而不是机械地只看昨天——但如果
  你无法确认上一次成功运行是哪天，退回使用上面两条默认规则，并在 `报告摘要.核心状态`/`备注` 里
  注明"窗口按默认规则计算，未确认上一次成功运行时间"，不要凭空断言窗口是连续覆盖的。

## 第二步：执行研究

在上面确定的研究窗口内，对每一条当前持仓 + 每一条高优先级观察名单条目，按
`prompts/daily-investment-report.md` 的流程和输出结构执行分析。可获得当前市场价格时可以填写 `当前价格`；将其与 `参考买入价/区间`（分别来自
`当前持仓.参考买入价/区间` 或 `观察名单.理想买入区间`）比较后写入 `价格位置`——只能从
`低于区间`/`区间内`/`高于区间`/`未知` 这四个精确值中选一个，不得发明"略高于区间"这类更细致的
表达；如果价格明显偏向区间上方但不确定具体幅度，仍然只能写 `高于区间`，不得为了更精确而造出新
措辞——这只是客观位置描述，不是买卖信号，你不得据此给出任何交易建议。三个字段（`参考买入价/区间`、
`当前价格`、`价格位置`）只要来源数据缺失，就必须留空（`价格位置` 留空时写 `未知`），绝不能编造。

## 观察候选的 canonical 建议动作（写入 报告持仓.IOS状态）

每个 资产类型=watchlist 的新报告行必须写入报告生成阶段已经判断的下一步研究动作，且只能使用：

- 研究建仓：正式研究是否建立初始仓位，不是立即买入；
- 等待估值：企业逻辑有吸引力，但估值研究或锚点尚不足；
- 等待价格：研究结论基本成立，但当前价格纪律不满足；
- 继续观察：保留候选，尚未达到建仓研究阶段；
- 降低优先级：相对现有持仓或其他候选机会成本较差。

这不是 Dashboard、价格或 CSS 推导出的标签。优先级（高/中/低）、价格位置 和 IOS状态 是独立维度，必须分别原样写入。Daily 只能根据既有 IOS 研究状态和本次新增证据输出当前下一步研究动作；不得扩展为完整 Deep Dive、每日组合配置、买卖数量或自动交易指令。

## 入场计划评估（写入 报告持仓.执行状态，第 298 号 issue，只读评估，不创建/修改计划）

对第一步按活跃计划选取规则（含并列版本的决胜/失效处理，见第一步的 `入场计划` 读取说明）确定的每一个
活跃 `入场计划` 行（按其 `代码` 匹配当前持仓/观察候选），用本次获得的当前价格与该计划的区间/条件
比较，写入：

- `入场计划ID`：该 `计划ID`；
- `入场计划估值锚点`：原样复制该计划版本自己的 `长期估值锚点`，不得改写、概括或重新估算；
- `执行状态`：只能是 `可小额开始`/`接近区间`/`等待价格`/`等待确认`/`暂停复核` 中的精确一个，按固定
  优先级顺序判定——完整定义与判定优先级见 `prompts/daily-investment-report.md`"入场计划评估"一节
  （该节已完整内嵌五值定义与优先级，不是仅链接到 Weekly prompt——Daily Task 运行时从不嵌入 Weekly
  的 prompt 文件，交叉引用在这里没有意义）；
- `当前区间`：价格所在的具体区间，或简短说明未落入任何区间；
- `需要复核`：通常留空——这是 Weekly 才需要主动判断并配上 报告待办 的字段。这个字段只针对一个
  已经可靠选定的具体计划版本；第一步遇到并列最高版本、无法可靠确定活跃计划的情形时，不适用这条
  规则，绝不设为真——那种异常只通过第一步已经写的那条 报告待办 上报，不通过 需要复核 传递。

**执行说明字段（第 303 号 issue 阶段一，与上面五个字段同一次评估写入）**：

- `入场计划版本`/`入场计划数据时间`：原样复制该计划版本自己的 `版本`/`数据时间`——只取决于选中了
  哪个计划版本，不依赖当前价格，和 `入场计划ID`/`入场计划估值锚点` 同一种形状。
- `停止条件说明`：来自计划自己的 `不追高条件`/`失效条件`——这两个来源与当前价格无关，所以这个
  字段和 `入场计划版本`/`入场计划数据时间` 同一种形状：可靠选定活跃计划即写入，不因本次缺少当前
  价格而留空（第二轮 review 修正）。必须和"卖出现有持仓"清楚区分。计划本身没有写明时必须写
  "计划未完善：……"提示，不能留空或编造停止条件。
- `较上次变化说明`：和该 `代码` 最近一次 Daily（不跨 Weekly 比较）仍然有效的历史报告行比较，区分
  计划版本变化/同一计划版本下的事实变化/"本次评估数据缺失，暂无法比较"（写"无法确认：……"提示，
  不是留空）/无变化；没有可比历史时写"首次评估，无可比历史"，不能编造对比。**形状同停止条件
  说明**：可靠选定活跃计划即写入。
- `行情截至时间`：本次评估所用 `当前价格` 的取价时间/口径说明；只有本次真正用到一个具体报价时才
  写入——没有可用的活跃计划、计划无法可靠选定、或当前价格本身缺失时都留空。评估成功但数据源未
  提供精确口径时，允许合法留空，不得为此编造时间。
- `当前阻碍` 与 `下次检查`：不跟随 `执行状态` 的留空形状，必须覆盖四种情况（第二轮 review 修正）：
  1. 没有可靠确定的活跃入场计划：固定说明——研究/估值尚未完成；`当前阻碍` 须说明现有 `参考买入价/
     区间`（如果有）不构成下单授权；`下次检查` 直接给出补全动作（先完成研究/估值，由 Weekly Deep
     Dive 制定入场计划），不是具体日期。
  2. 活跃计划因并列最高版本无法可靠选定：说明需人工核查清理，与已写入的 报告待办 一致。
  3. 活跃计划已可靠选定但当前价格等评估数据缺失：写成以"无法确认："开头的提示，说明具体缺了什么
     （例如"无法确认：当前价格缺失"），不能留空或编造猜测值。
  4. 活跃计划已可靠选定且评估成功：`当前阻碍` 从计划自己的 `技术确认条件`/`不追高条件`/`失效条件`
     与当前价格/区间关系中提炼；`下次检查` 来自计划自己的 `下一验证证据`/`计划复核触发`——这两个
     来源字段与当前价格无关，所以情况 3（价格缺失）下依然可以给出内容。计划本身没有写明对应条件时
     必须写"计划未完善：……"提示，不能留空或编造条件。

  `当前阻碍` 唯一的留空情况是情况 4 且 `执行状态=可小额开始`。`下次检查` 没有自己的留空情况。

"计划未完善：……"、"无法确认：……"、和没有活跃计划/并列版本时的固定说明是三种不同的提示，分别
对应"计划本身缺条件"、"本次评估数据缺失"、"没有可靠选定的活跃计划"——不能用留空代替任何一种。

**执行状态写入契约和发布门槛**：非空 `执行状态` 只能是 `可小额开始`/`接近区间`/`等待价格`/`等待确认`/`暂停复核`；`进入区间`、`不追高`、`暂停并复核`、`无 active 计划` 都不是允许值。不得把条件或没有计划的事实写入这个字段；没有可靠确定的活跃计划时 执行状态/当前区间/行情截至时间/入场计划ID/入场计划估值锚点/入场计划版本/入场计划数据时间/停止条件说明/较上次变化说明/需要复核 十个字段留空（但 当前阻碍/下次检查 按上面情况 1 写入固定说明，不属于"留空"的范围）。第三步第 4 小步切换 `报告摘要` 前，必须重新读取本次暂存的所有 `报告持仓.执行状态`，逐行确认每个非空值都在这五值白名单内；发现无效值时须在同一 `生成ID` 内按固定优先级修正后重新校验，校验仍失败则不得切换摘要或发送成功通知。

Daily **绝不**创建、修改、原地更新 `入场计划` 本身的任何字段（长期估值锚点、计划新增仓位说明、
区间、占比、技术确认条件、不追高条件、失效条件）——那是 Weekly Deep Dive 的职责。写入这十二个
字段必须精确区分三种情况，不能笼统地"缺什么就留空"：

- **没有可靠确定的活跃入场计划**（不存在，或存在并列最高版本且数据时间也无法区分）：`入场计划ID`/
  `入场计划估值锚点`/`入场计划版本`/`入场计划数据时间`/`行情截至时间`/`执行状态`/`当前区间`/
  `需要复核`/`停止条件说明`/`较上次变化说明` 十个字段留空，继续只写 参考买入价/区间/价格位置，
  和这个功能存在之前完全一样；`当前阻碍`/`下次检查` 按上面情况 1/2 写入固定说明，不属于"留空"的
  范围。
- **活跃计划已经可靠选定，但本次缺少当前价格等评估数据**：`入场计划ID`/`入场计划估值锚点`/
  `入场计划版本`/`入场计划数据时间`/`停止条件说明`/`较上次变化说明`（此时写"无法确认：……"提示，
  不是留空）仍然必须按该计划版本写入；`执行状态`/`当前区间`/`行情截至时间` 因为无法评估而留空；
  `当前阻碍`/`下次检查` 按上面情况 3 写入"无法确认：……"提示；`需要复核` 通常也留空。绝不能因为
  价格缺失就连 `入场计划ID`/`入场计划估值锚点`/`入场计划版本`/`入场计划数据时间` 也一起清空——
  那会让 Dashboard 退回到旧的 参考买入价/区间 显示，和一个真实存在的活跃计划互相矛盾。

源数据缺失绝不编造，只影响 执行状态/当前区间/行情截至时间（留空）以及 当前阻碍/下次检查/
较上次变化说明（写"无法确认：……"提示，不是留空），不影响已经可靠选定的 入场计划ID/入场计划
估值锚点/入场计划版本/入场计划数据时间/停止条件说明。

## 订单准备评估与执行反馈（写入 报告持仓.准备状态，第 303 号 issue 阶段二）

Daily **绝不**设定订单执行参数（`入场计划` 的 `计划新增仓位币种`/`计划新增仓位金额`/`订单类型`/

`换汇可行性确认`/`订单资金账户` 都只由 Weekly Deep Dive 设定或核对）——这里只读取这些参数做机械换算/核对，
绝不独立设定预算、阈值、买点或配置。完整判定规则见 `prompts/daily-investment-report.md`"订单
准备评估与执行反馈"一节（该节已完整内嵌，不仅链接到 Weekly prompt）。在十二个阶段一字段之后，
继续写入：

- `准备状态`：按固定七步顺序判定，**数据缺失和无计划/并列异常是两种不同的情况，绝不合并为
  一个"留空"**：(1) 无计划/并列异常 → 留空；(2) 活跃计划可靠选定但数据缺失（`执行状态` 本身
  为空，不含情形 1）→ `无法确认`；(3) `执行状态` 非空但不是 `可小额开始` → `无需准备`；
  (4) `执行状态=可小额开始` 时，沿该区间自己的 `区间N上一版本对应区间` 显式指针逐层回溯血缘
  链查 `入场执行反馈`（**不是**按"区间1/2/3"标签直接跨版本匹配——一次修订可能把上一版本的

  **任意一层完全不存在任何记录 → `无法确认`**（缺少记录不等于没有订单，用户可能已自行下单
  但没告诉系统，绝不能当作"安全可以准备"而继续）；某一层最新记录为 `已挂单`/`部分成交`/
  `已成交`（未过期）→ `已有有效订单不重复建议`（部分成交也不重新计算剩余额度；这一阻断不因
  计划后来被修订而失效，链条会一路追溯到那一层）；为 `未知`，或 `已挂单`/`部分成交` 但
  `订单有效期截止` 已过期且无更新 → `无法确认`；为 `未下单`/`已取消` 且其 `数据时间` 不早于
  那一层计划版本自己的 `数据时间`：**还必须检查这个 (计划ID,区间) key 整段历史（不只是这
  一条最新记录）是否曾经出现过非空且大于零的 `已成交数量`，或者任意一行本身的 `订单状态`
  就是 `部分成交`/`已成交`**（哪怕是这条取消/未下单记录自己留空——`已成交数量` 是可选字段，
  留空代表"未填报"而不是"零成交"，状态本身就是证据，PR #305 round 7 review，round 8 修正）——
  出现过就不是真正"干净"，直接 → `无法确认`（取消/未下单不能撤销已成交部分）；整段历史既
  没有非零已成交数量、也没有 部分成交/已成交 状态时，**还必须检查这个 key 历史上（包括这条

  记录成交不等于真的零成交；`已取消` 本身也意味着订单曾经存在，不能因为从未单独看到过
  `已挂单` 就豁免——哪怕这个 key 第一条/唯一一条反馈就是 已取消）——如果历史上任意一行

  `无法确认`；只有整段历史都是 未下单 的 key 才不需要这条确认，才是真正"干净"的，链条

  那一层计划修订 → `无法确认`（需要重新确认）；(5) 价格政策须明确（见下方"价格政策前置检查"），且计划的
  订单参数（`订单类型`/`订单有效期`/`计划新增仓位金额`/`计划新增仓位币种`）、以及
  `交易单位确认`/`订单类型可用性确认`（两者始终必须非空）、`换汇可行性确认`（仅当
  `计划新增仓位币种` 与 `订单资金账户` 在 `账户状态` 里的 `币种` 不同时才要求非空）全部满足
  **且新鲜且绑定同一资金账户**才继续 (6)——对应的 `确认时间` 必须满足 0≤（报告日期−确认
  时间）≤30 天（未来日期不算新鲜）；`订单资金账户`（替代旧版 `换汇可行性确认账户`，绑定

  整条计划血缘，不只是活跃版本自己的区间——先对活跃版本每个非空区间按 (4) 同样方式查链条，
  标记查到的 (计划ID,区间) 为"已覆盖"；再找出整条血缘里所有非空区间中不在"已覆盖"里的"孤儿
  区间"（例如上一版本有的区间这次修订没有保留、也没被任何新区间指回），同样查它们的链条并
  标记覆盖，直到没有遗漏。任意一条链无法确定 → 这个区间也写 `无法确认`；有有效订单的区间，
  按那笔记录 `关联计划ID` 指向的历史计划版本自身数字（不是当前版本重新换算的数字）计算占用
  额度——但那个历史版本自己的 `计划新增仓位币种` 必须与活跃版本一致，不一致也算无法确定（PR
  #305 round 6 review finding #1，不能把不同币种的数字直接相减）；加总后从当前 `计划新增
  仓位金额` 减去得到剩余额度；本次所需规模超过剩余额度 → `无法确认`，否则继续 (7)；
  (7) `账户状态` 里 `账户`=`订单资金账户` 那一行必须明确提供、**币种与 `计划新增仓位币种`
  完全一致**（不能拿不同币种的数字直接比大小）、且 `数据时间` 满足 0≤（报告日期−数据时间）
  ≤7 天且不是未来日期（PR #305 round 6 review finding #2），才能判断是否明显足够而写
  `可准备订单`（不是随便一个同币种账户）；没有这个账户、币种不一致、数据时间缺失/未来
  日期/超过 7 天、或金额不足，这些情况都写 `无法确认`——未知的现金状况和已知不足一样不能
  放行。完整判定细节见 `prompts/daily-investment-report.md`"订单准备评估与执行反馈"一节。
- 价格政策前置检查（第 306 号 issue，方案 A）：当前区间的 `区间N价格` 必须本身就是单一价格或明确写出最高价（例如"≤180"），或者计划的 `订单类型` 明确规定"区间上沿为该批次最高限价"；只给范围且计划没有这条明确规则 → `计划未完善停在核对`（第 306 号 issue，维护者选定方案 A：不能把区间上沿自动升格为限价，`建议限价` 路径也不能绕过）。按计划明确规则从范围里取上沿时，`建议限价`/`计划买入上限` 写这个上沿并注明依据（例如"11 USD（区间1 上沿，按计划订单类型规则）"）；这是对计划明确规则的机械摘录，不是 Daily/Weekly 自己的判断。
- `建议限价`/`建议订单规模说明`：只在 `准备状态=可准备订单` 时写入，分别是对 `入场计划.区间N
  价格` 的机械摘录、以及 `区间N占比` x `计划新增仓位金额` 的一次乘法——不是 Daily 自己决定的
  价格/规模。到这一步时所有前置检查都已经过，不需要再追加免责声明。
- `计划订单有效期`/`最近订单状态`：原样复制该计划版本自己的 `订单有效期`、以及按上面 (4) 同样
  血缘链找到的最新一条相关记录的 `订单状态`；形状与 `入场计划版本` 一致（活跃计划可靠选定
  即写入）。
- `跳空处理提示`：只在检测到跳空越过计划区间限价、且计划设置了 `跳空处理规则` 时才摘录；没有
  跳空或计划没有设置规则时留空。

**记录用户的执行反馈**：仅在用户本次会话明确陈述了某个代码/区间的订单状态时，先做幂等检查
（今天是否已有内容完全相同的一行，有则不重复写入），再写入一条新的 `入场执行反馈` 行（`反馈ID`
全新、`关联计划ID` 指向用户实际说的那笔订单所属的计划版本——通常是当前活跃计划，但用户明确说
的是更早版本时就写那个更早的 `计划ID`，无法判断时改为写 `报告待办` 提示人工澄清；`订单状态`
用六值枚举之一的精确值、`数据时间` 为本次报告日期）；没有用户陈述就不写新行，绝不凭价格变化或
时间推断/编造。

## 今日行动摘要（写入 报告持仓.今日行动，第 306 号 issue）

完整规则见 `prompts/daily-investment-report.md`"今日行动摘要"一节（已内嵌）；这里只列运行时必须遵守的要点。在全部阶段一/
阶段二字段之后，每一行 `报告持仓` 再写入三个字段——只是对本行已写好字段的固定映射/机械摘录，不是
新的投资判断，Dashboard 只原样显示：

- `今日行动`：按顺序取第一个命中的——`入场计划ID` 为空且本次成功读取的 `入场计划` 里该代码没有

## `报告待办` 的跟进类型分类（第 267 号 issue，不改变第二步的研究判断，只补充结构化输出要求）

写入 `报告待办` 的每一行，除了原有的 `状态`（完成状态：`待处理`/`已完成`）之外，还需要额外写入
`跟进类型` 字段，用三个值之一区分这条后续事项属于哪一类，避免把"需要持续观察的条件"或"要等外部
事件才能推进的事项"误当成尚未完成的实质待办工作，在 Dashboard 上制造虚假的积压感：

- `可执行`：现在就可以推进的实质性研究/复盘/计算工作（例如"核实某公司 Q3 财报中的毛利率变化"）。
- `持续观察`：需要在未来多期报告中持续跟踪的条件或指标，本身不是一次性可完成的任务（例如"持续
  观察某芯片新产品的产能爬坡、毛利率、库存/DSO 变化"，"持续观察就业/通胀/利率对估值的影响，不做
  宏观择时"）。
- `等待证据`：在某个外部事件（财报、董事会决议、监管批复等）发生之前，没有可执行的下一步动作
  （例如"等待公司董事会对分拆方案的正式决议后再评估"）。

规则：

- 每条 `报告待办` 行都应该写这个字段；如果判断不出属于哪一类，留空即可——Dashboard 会把空值/无法
  识别的值一律当作 `可执行` 处理（最保守的默认，不会把应有的关注度错误地隐藏起来），不需要猜测。
- `跟进类型` 与 `状态`（完成状态）是两个独立维度：一条 `持续观察`/`等待证据` 的事项，只要它描述的
  条件仍然成立，`状态` 通常保持 `待处理`；只有当这条跟进事项本身彻底结束（例如相关事件已经落地、
  不再需要继续观察）才把 `状态` 改成 `已完成`。不要为了让 Dashboard 看起来"没有待办"而把仍在进行的
  观察/等待项标记为已完成。
- 同一个持续监控的条件在连续多次 Daily 报告里重复出现是正常状态，不代表任何东西被遗漏或延误——
  `跟进类型`=`持续观察` 正是为了让 Dashboard 不把这种重复识别成积压中的未完成工作，这一节只改变
  Sheet 里怎么标记，不改变第二步应该研究、判断、写出什么内容。
- 不得用 `跟进类型` 掩盖真正的、当下就能推进的实质性工作——只有确实不是"现在就能做的事"才归为
  `持续观察`/`等待证据`，其余一律 `可执行`（含未标注时的默认值）。

## 第三步：写回 Sheet（必须遵循 report_write_protocol，绝不能跳步）

完整协议定义见 `setup/schema/sheet-schema.json` 的 `report_write_protocol` 字段和
`docs/v2.1-architecture.md` 的 "Report write protocol" 一节。执行顺序：

**诊断边界（第 296 号 issue）**：如果本次运行在第 1 步生成新 `生成ID` 之前就失败（例如读取 Sheet
之前的工具调用失败、研究阶段中断、执行环境超时或异常终止），必须把这次失败明确标记为
**运行时/平台执行失败**，绝不能诊断成"Sheet 原子写入失败"——因为 report_write_protocol 从未被
进入，`报告摘要` 仍然指向上一次成功运行的旧 `生成ID`（或对首次运行保持不存在），Dashboard 展示
不受影响。只有在第 1 步已经生成了新 `生成ID`、协议本身的某一步（第 4 步校验或第 6 步确认）失败时，
才归类为写入协议内部的失败；两者是不同的失败类别，混淆诊断会掩盖真正的运行时稳定性问题。

1. **生成 ID**：为本次运行生成一个全新的 `生成ID`（例如 UUID），不要复用任何一次历史运行的值，
   包括失败重试。
2. **规划期望内容与数量**：在写入任何一行之前，先确定本次生成完成后，`报告持仓`（`资产类型=holding`）、
   `报告持仓`（`资产类型=watchlist`）、`报告风险`、`报告待办` 这四个部分各自应该包含哪些具体条目
   （每个持仓/观察名单行用它的 `代码`/`名称` 标识，每条风险/待办用本次分析已经确定的具体内容标识）
   以及由此推出的行数——不能只定一个数字，因为暂存时"漏掉一条该写的、多写一条重复的"可以让行数
   刚好对上却仍然是错的；不能等暂存完之后再从"实际写了多少行/写了哪些"倒推。**Daily 的
   `资产类型=watchlist` 范围只能是本次第一步读到的、`优先级=高`（含迁移前遗留的英文值 `high`）
   的观察名单条目**——不是全部观察名单（全量观察名单周度复盘是 Weekly 专属的第 293 号 issue 范围，
   Daily 不得扩大到覆盖全部观察名单，也不得因为"图省事"而缩小到比这更窄的子集）。第 4 步的校验
   只有对照这里先固定下来的条目与数量才有意义。
3. **暂存**：把本次生成应该存在的**全部** `报告持仓`/`报告风险`/`报告待办` 行写入 Sheet，每一行
   都带上 `(报告ID, 生成ID)`——不是只写本次运行重新计算过的那部分；哪怕某一行这次没有变化，也
   必须在新的 `生成ID` 下重新写入，绝不能让它继续留在旧 `生成ID` 下。**一个 `生成ID` 绝不能只
   覆盖部分表/部分行**——只把其中一张表或一部分行写入新 `生成ID`、其余仍留在旧 `生成ID`，会让
   Dashboard 在切换后把这些行当作不存在（读取端只认精确匹配当前 `报告摘要.生成ID` 的行），这正是
   第 293 号 issue 记录的 2026-09-05 真实事故的成因。`报告ID` 格式固定为 `daily-YYYY-MM-DD`
   （`YYYY-MM-DD` 是本次报告的 `报告日期`，不是运行时间戳）。此时**不要**修改 `报告摘要` 中已有
   的行——在这一步完成之前，Dashboard 和其它读者看到的仍然是上一次成功运行的旧版本。
   **写入方式（第 306 号 issue，2026-10-16 事故）**：暂存只能用工具“追加到表格末尾、插入新行”的方式
   （例如 Sheets `values.append`）写入；绝不先读一次“第一个空行”再按算好的固定行号/区域（如
   `A2808:AR2822`）写入，也绝不改写任何原本非空的行。Daily 与 Weekly 可能同时运行并共用报告 tab，
   按事先算好的行号写入会互相覆盖。2026-10-16 23:31 两份报告同时运行后，已发布的 Weekly 只剩 16/31 行、
   摘要却仍写 31 条；从行布局推断是 Daily 覆盖了 Weekly 的 15 行，尚无写入日志证实。“先读回目标区域
   确认为空再按区域写入”**不算**安全做法：读和写是分开的两步，另一份报告可能在两步之间写入同一区域，
   甚至在本次已经校验、切换、确认之后才覆盖。所以本次运行可用的写入工具不支持服务端原子追加（插入
   新行）时，**不要暂存任何行**：停在第 3 步之前，`报告摘要` 保持指向上一次成功的 `生成ID`，运行状态
   写明“Blocked：写入工具不支持原子追加”。第 4、6 步按
   `代码` 集合逐一核对；`报告摘要` 的 `当前持仓数`/`高优先级观察数` 以及 `一句话结论`/`核心状态`
   里写的条目数，必须取第 4 步实际读回的结果，不能照抄第 2 步的计划。
4. **校验（切换前，失败即终止）**：把刚写入的 `(报告ID, 生成ID)` 行读回来，与第 2 步预先定好的
   期望内容逐一比对——既要比对每个部分的行数，也要逐条核对具体条目（代码/名称，或风险/待办的具体
   内容）是否与第 2 步计划的完全一致；不是"看起来差不多"，也不是回头用刚写入的行反过来当作预期。
   行数刚好对上、但漏掉了计划中的某一条、同时多出另一条重复/错误条目，同样算校验失败。只要有任何
   一个部分的行数或具体条目对不上（包括第 2 步预期非零、但实际暂存为零的部分），立刻停止：不要写
   `报告摘要`，直接把这次运行标记为失败（通过你自己的运行状态/通知渠道说明，不要往 `报告摘要`
   里写任何东西）。
5. **切换**：只有第 4 步校验通过之后，才创建或更新 `报告ID` 对应的那一行 `报告摘要`，把它的
   `生成ID` 字段设置为新值。这一步、也只有这一步，才是真正的"发布"——在此之前的任何失败都不会让
   用户看到不完整的报告。
6. **确认（切换后，失败即终止通知）**：切换完成后，重新读取这个 `报告ID` 的 `报告摘要`，确认它的
   `生成ID` 确实等于刚写入的新值；再按精确的 `(报告ID, 生成ID)` 重新读取
   `报告持仓`/`报告风险`/`报告待办`，重新按第 4 步同样的方式比对——行数与具体条目都要重新核对，
   确认仍然与第 2 步的计划完全一致。只有这一步确认通过，才能在第五步发送成功通知。如果确认
   失败——读回来的 `生成ID` 不对、任何一个部分的行数或具体条目对不上、或者这次重读本身失败——
   即使 `报告摘要` 已经切换过去了，也绝不能发送成功通知；必须通过运行状态说明失败，因为这次失败
   发生在发布之后，跟第 4 步的失败不是一回事，同样需要被看见。
7. 如果同一个 `报告ID` 已经存在于 `报告摘要` 中（同一天被重复触发），照样走完整流程 1–6；新的
   `生成ID` 会成为新的当前版本，旧版本的明细行会成为孤立数据（Dashboard 会自动忽略它们，你不需要
   手动删除，但如果方便的话可以清理）。

## 第四步：`报告摘要` 内容要求

- `报告类型` = `daily`
- `报告日期` = 本次报告覆盖的日期（`YYYY-MM-DD`）
- `一句话结论`：一句话概括今天最重要的判断
- `核心状态`：正常状态写"正常"或类似的简短描述；Blocked 状态必须写清楚具体原因（例如"当前持仓 tab
  缺少 状态 列，无法判断持仓"）
- `当前持仓数`/`高优先级观察数`：分别是本次读取到的当前持仓行数、高优先级观察名单行数
- `生成时间`：本次运行的时间戳（ISO 8601，UTC 或带时区偏移）

  `purchase_plan_modes_supported` 声明里时继续生成报告——这些都是 Blocked（第 318 号 issue）；

  `建议限价`，不从长期估值或 `入场计划.区间N价格` 补，不在 `legacy` 下展示或引用，不信任存储的
  `技术参考与上限关系` 标签。
- 不发布未通过"五项首屏与发布前校验"七项检查的行，不把无有效分档写成 `等待确认`，不把 `计划买入上限`

  非空条件（第 306 号 issue）。
- 不自主交易，不给出任何买入/卖出/加仓/减仓指令。
- 不编造任何持仓、价格、参考区间数据——缺失就是缺失，写明或留空。
- 不在 Sheet 数据不可用时，退回使用聊天历史里的旧持仓信息代替。
- 不跳过 report_write_protocol 的任何一步，不直接覆盖 `报告摘要` 而不先完成暂存与校验。
- 不在第三步第 4 小步的切换前校验、或第 6 小步的切换后确认失败时，仍然发送成功通知——两者任一
  失败都必须改为按运行状态说明失败，即使 `报告摘要` 已经切换过去了。
- 不在 Sheet 绑定、时区占位符或内容权威 EMBED 占位符未被替换时继续运行——任一仍是占位符文本都是
  Blocked 状态，必须先停止并说明原因，不得凭猜测代替。
- 不用"最近的新闻"这类笼统说法代替上面"研究窗口"一节定义的具体时间范围——尤其是周一的运行必须
  覆盖周末，不能只看过去 24 小时。
- 不创建、修改或重新估算 `入场计划` 本身的任何字段（长期估值锚点、计划新增仓位说明、区间、占比、
  技术确认条件、不追高条件、失效条件）——Daily 只读取并评估已有的活跃计划，制定和实质更新计划是
  Weekly Deep Dive 的职责。
- 不在 `报告持仓.执行状态` 判定时跳过固定优先级顺序凭感觉挑值；非空值绝不写成 `进入区间`/`不追高`/`暂停并复核`/`无 active 计划` 等别名；不改写、概括 `入场计划估值锚点`——必须原样复制所引用计划版本自己的长期估值锚点。
- 不在活跃计划出现并列最高 `版本` 且 `数据时间` 也无法区分时凭行顺序或猜测选择其中一行——必须按
  "无法可靠确定活跃计划"处理（`入场计划ID`/`入场计划估值锚点`/`入场计划版本`/`入场计划数据时间`/
  `行情截至时间`/`执行状态`/`当前区间`/`需要复核`/`停止条件说明`/`较上次变化说明` 十个字段全部
  留空/留假，需要复核 也不设为真）并写入对应 `报告待办`；`当前阻碍`/`下次检查` 仍须按固定说明
  写入，不属于"留空"的范围。
- 不在活跃计划已经可靠选定、只是当前价格等评估数据缺失时，连同 `入场计划ID`/`入场计划估值锚点`/
  `入场计划版本`/`入场计划数据时间`/`停止条件说明` 一起清空——这些字段只取决于选中了哪个计划版本
  和计划自身条件，必须继续写入；只有 `执行状态`/`当前区间`/`行情截至时间` 因无法评估而留空；
  `当前阻碍`/`下次检查`/`较上次变化说明` 这种情况下必须写"无法确认：……"提示，也不是留空。
- 不在 `入场计划ID` 为空时把 `需要复核` 设为真——`需要复核=true` 只能出现在 `入场计划ID` 同时
  非空的行上。
- 不把 当前阻碍/下次检查 和 执行状态 绑在一起留空——没有活跃计划、并列版本异常、或评估数据缺失
  时，这两个字段仍须写入对应的固定说明或"无法确认：……"提示，不得留空；当前阻碍 唯一的留空情况
  是活跃计划已可靠选定、评估成功、且 执行状态=可小额开始；下次检查 没有自己的留空情况。
- 不在活跃计划已可靠选定且评估成功、但计划本身没有写明对应条件（技术确认条件/不追高条件/失效
  条件/下一验证证据/计划复核触发）时，把 当前阻碍/下次检查/停止条件说明 留空或编造条件——必须写
  "计划未完善：……"提示；不得把"计划未完善：……"和"无法确认：……"两种提示混用，前者指计划本身
  缺条件，后者指本次评估数据缺失。
- 不把 停止条件说明 写成或被理解为对已持有部分的减持/清仓判断——它只说明取消/暂停本次计划内新增
  买入的条件。
- 不在没有可比历史报告行时编造 较上次变化说明 的对比内容——必须写"首次评估，无可比历史"。
- 不在价格缺失时连同 `入场计划版本`/`入场计划数据时间`/`停止条件说明`/`较上次变化说明`（写
  "无法确认：……"提示，不是留空）一起清空——这些字段只取决于选中了哪个计划版本和计划自身条件。
- 不为 `行情截至时间` 编造一个数据源没有提供的精确时间——数据源未给出明确口径时，这个字段允许
  合法留空，不是"计划未完善"。
- 不创建、修改或重新估算 `入场计划` 的任何订单执行参数（计划新增仓位币种、计划新增仓位金额、
  订单类型、订单有效期、跳空处理规则）——这些只由 Weekly Deep Dive 设定，Daily 只读取并机械
  换算/核对。
- 不独立设定预算、阈值、买点或配置，不做独立交易决策——`建议限价`/`建议订单规模说明` 必须是对
  入场计划 已有数值的机械摘录/换算，绝不是 Daily 自己研究或决定的价格/规模。
- 不在计划缺少订单参数（订单类型/订单有效期/计划新增仓位金额/计划新增仓位币种任一为空）时，仍把
  `准备状态` 写成 `可准备订单` 并编造缺失的限价/规模——必须停在 `计划未完善停在核对`。
- 不把"执行状态 本身为空因为数据缺失"和"没有活跃计划/并列异常"合并成同一个"准备状态 留空"
  ——前者必须写 `无法确认`，只有后者才留空；两者混为一谈会让一个真实存在但本次评估不了的计划
  被误当作"没有计划"（PR #305 review finding #1）。
- 不把"完全没有 `入场执行反馈` 记录"当作"没有占用中的订单"而继续往下走——必须写 `无法确认`；
  缺少记录不等于没有订单，用户可能已经自行下单但没告诉系统（PR #305 round 2 review finding
  #1）。
- 不在 `入场执行反馈` 的 `订单状态=未知`、或 `已挂单`/`部分成交` 但 `订单有效期截止` 已过期
  且无更新时，仍把 `准备状态` 放行到 `可准备订单`——这些情况必须写 `无法确认`，未知/过期绝不
  等于"没有订单"（PR #305 review finding #2）。
- 不在遇到 `部分成交` 时重新计算 `剩余待成交数量` 对应的剩余额度、也不为剩余部分重新给出一条
  `建议订单规模说明`——已挂单/部分成交/已成交（未过期）统一写 `已有有效订单不重复建议`，剩余
  部分留给用户自己核对（PR #305 review finding #2/#5）。
- 不在这个 (计划ID,区间) key 之前出现过非零 `已成交数量`，或者曾经有任意一行 `订单状态` 本身
  就是 `部分成交`/`已成交`，之后让后续一条 `已取消`/`未下单` 记录把这个区间重新判定为
  "干净"——取消/未下单描述的是剩余未成交部分的状态，绝不代表已经买入的那部分凭空消失；即使
  这条取消/未下单记录自己把 `已成交数量` 留空，也不能当作"之前没成交"，必须回看这个 key 整段
  历史；`已成交数量` 是可选字段，留空代表"未填报"而不是"零成交"，所以 部分成交/已成交 状态
  本身就是证据，哪怕从未填过数量——只要历史上任意一行出现过非零 已成交数量或这类状态，就
  必须写 `无法确认`，不能放行到 `可准备订单`（PR #305 round 7 review，round 8 修正）。
- 不在这个 key 从未对这条 `已取消`/`未下单` 记录明确要求 `已成交数量=0`（显式零）的情况下，
  就把它当作"已核实零成交"——只要这个 key 历史上（包括这条记录自己）曾经出现过意味着订单
  存在过的状态，取消/未下单记录自己留空 `已成交数量` 绝不能被当作安全的零成交；这个系统没有
  券商自动同步，已挂单 和 取消/未下单 两次上报之间可能发生过未被上报的部分成交（PR #305
  round 9 review）。不在这个 key 第一条/唯一一条反馈就是 `已取消` 时，因为系统从未单独看到
  过一条 `已挂单` 记录就豁免这条确认——`已取消` 本身就意味着曾经有订单存在（PR #305 round
  10 review）。只有整段历史（包括这条记录自己）都是 未下单 的 key 才不需要这条显式零确认。
- 不在计划被 Deep Dive 修订之后，就认为旧版本下遗留的 `已挂单`/`部分成交`/`已成交` 记录与当前
  区间无关而解除阻断——血缘链会一路追溯到那一层，这条阻断必须原样保留（PR #305 round 2 review
  finding #2）。
- 不把唯一能放行的 `未下单`/`已取消` 确认当作永远有效——必须检查它的 `数据时间` 是否不早于
  那一层计划版本自己的 `数据时间`；早于那一层计划修订的旧确认必须改判 `无法确认`，要求重新
  确认，不能直接当作仍然适用（PR #305 round 2 review finding #1/#2）。
- 不在查找该代码/该区间最新 `入场执行反馈` 记录时按"区间1/2/3"标签直接跨版本匹配——必须沿着
  `区间N上一版本对应区间` 的显式指针逐层回溯，因为一次修订可能把同一笔资金从一个编号调整成
  另一个编号，凭编号匹配会找错层或找不到（PR #305 round 3 review finding #1，取代 round 2
  的做法）。
- 不在 Deep Dive 铸造新计划版本（`上一版本ID` 非空）时，让某个非空 `区间N价格` 的
  `区间N上一版本对应区间` 留空——必须明确写上一版本对应的区间标签，或者"新增资金"；读到
  这种违反写入不变量的历史行时，评估该区间要停在 `无法确认`，不能凭编号猜测对应关系（PR
  #305 round 3 review finding #1）。
- 不在计划的 `交易单位确认`/`订单类型可用性确认` 缺失、或币种不一致时 `换汇可行性确认` 缺失
  时，仍把 `准备状态` 写成 `可准备订单`——必须停在 `计划未完善停在核对`，不编造确认内容（PR
  #305 round 3 review finding #2）。
- 不把超过 30 天未更新、或确认时间晚于本次报告日期（未来日期）的 `交易单位确认时间`/
  `订单类型可用性确认时间`/`换汇可行性确认时间` 当作仍然有效——必须视为对应确认缺失，停在
  `计划未完善停在核对`，不因为确认文字本身还在就当作仍然适用；未来日期不能因为时间差是负数
  就误判为满足≤30天（PR #305 round 4 review finding #1，round 5 修正）。
- 不在 `订单资金账户` 缺失、或与这次实际用来核对现金的那个 `账户状态.账户` 不一致时，仍采信
  `交易单位确认`/`订单类型可用性确认`/`换汇可行性确认`——这三项确认（不只是换汇）都绑定同一个
  `订单资金账户`，缺失或账户不一致都等同确认缺失（PR #305 round 4 review finding #1，round 5
  改用统一字段替代旧版只绑定换汇的 `换汇可行性确认账户`）。
- 不只核对正在评估的这一个区间自己的血缘链就放行 `可准备订单`——必须核对整条计划血缘（不只是
  活跃版本自己的区间）的占用情况，包括活跃版本没有继任者的历史"孤儿区间"（例如上一版本有的
  区间这次修订没有保留、也没被任何新区间指回）；血缘里任意一处状态无法确定时，这个区间也必须
  写 `无法确认`，不能只看自己这个区间干净就放行（PR #305 round 4 review finding #2，round 5
  扩大覆盖范围到整条血缘）。
- 不用当前计划版本重新换算的数字计算已占用的额度——必须用那笔 `入场执行反馈` 记录自己
  `关联计划ID` 指向的那个历史计划版本自身的 `区间{对应标签}占比` x 那个版本自己的 `计划新增
  仓位金额`，即下单当时实际承诺的数字（PR #305 round 4 review finding #2）。
- 不在核对现金时匹配"任意一个币种相同的 账户状态 行"——必须精确匹配 账户=订单资金账户 的那
  一行，两个账户即使币种相同也不是同一个账户（PR #305 round 5 review finding #1）。
- 不把不同币种的现金数字直接拿来和订单规模比大小——`账户状态.币种` 必须与 `计划新增仓位币种`
  完全一致才能继续核对金额是否足够，这个系统不做任何换汇计算（PR #305 round 6 review finding
  #1）。
- 不把超过 7 天未更新、或 `数据时间` 晚于本次报告日期（未来日期）的 `账户状态.可用现金` 当作
  仍然有效——现金核对的新鲜度窗口比人工确认的 30 天更短，因为现金余额变化更频繁（PR #305
  round 6 review finding #2）。
- 不在计算历史区间已占用额度时，忽略那个历史计划版本自己的 `计划新增仓位币种` 和活跃版本是否
  一致——币种不一致时也必须判定为无法确定计划剩余额度，不能把不同币种的数字直接相减（PR #305
  round 6 review finding #1）。
- 不在用户没有在本次会话明确陈述订单状态时，新增、推断或编造一行 `入场执行反馈`——没有用户陈述
  就不写新行，沿用已有的最新记录。
- 不在写入 `入场执行反馈` 新行前跳过幂等检查——如果今天已经写过内容完全相同的一行，这是一次
  重复确认或 Task 重试，不再写第二行（PR #305 review finding #4）。
- 不把用户陈述的订单强行绑定到当前活跃计划——用户明确说的是更早一个版本下准备的订单时，
  `关联计划ID` 必须写那个更早的 `计划ID`；无法判断用户指的是哪个版本时，这次不写新行，改为
  写 `报告待办` 提示人工澄清，不得凭猜测绑定（PR #305 review finding #3）。
- 不在 `账户状态` 不存在、没有覆盖对应币种、或提供了但金额不足时，仍把 `准备状态` 写成
  `可准备订单`——这三种情况都必须写 `无法确认` 并在 `当前阻碍` 写明缺失或不足的具体现金数据；
  未知的现金状况和已知不足一样不能放行（PR #305 round 2 review finding #3）。只有现金已验证
  且充足、且其余全部前置确认也都齐全时，才能写 `可准备订单`——到这一步不需要再额外追加免责
  声明。
- 不把 `入场执行反馈.已成交` 状态当作 当前持仓/交易记录 的事实来源，也不用它覆盖两者——出现
  不一致时提示人工核对，不自行判定哪个对。
